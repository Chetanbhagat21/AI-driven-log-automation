### Issue Title
`CRITICAL`: Inconsistent User Balances during Concurrent Transaction Requests

### Issue Description
We are seeing intermittent discrepancies in user balances when multiple API calls to `/api/v1/wallet/debit` are made simultaneously for the same user. 

**Steps to Reproduce:**
1. Send 5 concurrent POST requests to debit $10 from a user with a $50 balance.
2. Expected result: Balance should be $0.
3. Actual result: Balance often ends up at $30 or $40.

**Current Code Snippet:**
```javascript
const user = await User.findById(userId);
if (user.balance >= amount) {
    const newBalance = user.balance - amount;
    await User.updateOne({ _id: userId }, { balance: newBalance });
}
```

---

### 1. Root Cause
The issue is a classic **Race Condition (Lost Update)**. 

In the current implementation, the Node.js application performs a "Read-Modify-Write" cycle at the application level:
1. **Read:** The application fetches the current balance from MongoDB.
2. **Modify:** The application calculates the new balance in memory.
3. **Write:** The application sends the new value back to the database.

Under high concurrency, two or more requests can perform the **Read** step at the same time, seeing the same initial balance. Both calculate a new balance based on that same initial value and send a **Write** request. The last write simply overwrites the previous one, causing the intermediate transactions to be "lost."

---

### 2. Fixed Code

The solution is to move the logic into the database layer using an **atomic update** or **optimistic concurrency control**.

#### Option A: Atomic Update (Recommended for simple increments/decrements)
```javascript
/**
 * Debits the user balance using an atomic $inc operator.
 * This ensures the calculation happens inside the DB engine.
 */
async function debitUserBalance(userId, amount) {
    const result = await User.findOneAndUpdate(
        { 
            _id: userId, 
            balance: { $gte: amount } // Check sufficiency atomically
        },
        { 
            $inc: { balance: -amount } 
        },
        { 
            new: true, // Return the updated document
            runValidators: true 
        }
    );

    if (!result) {
        throw new Error('Insufficient funds or User not found');
    }

    return result.balance;
}
```

#### Option B: Transactions (If complex logic is required)
If we needed to log a transaction history record simultaneously, we would use a Managed Transaction:
```javascript
const session = await mongoose.startSession();
await session.withTransaction(async () => {
    const user = await User.findById(userId).session(session);
    if (!user || user.balance < amount) {
        throw new Error('Insufficient funds');
    }
    
    user.balance -= amount;
    await user.save({ session });
    
    await TransactionHistory.create([{
        userId,
        amount,
        type: 'debit'
    }], { session });
});
await session.endSession();
```

---

### 3. Explanation
*   **Atomic Operators:** By using MongoDB's `$inc` (or SQL's `SET balance = balance - value`), we eliminate the need to fetch the value into Node.js memory. The database engine handles the operation as a single, indivisible unit of work.
*   **Predicate Check:** Adding `balance: { $gte: amount }` to the query filter ensures that we only perform the update if the condition is met at the exact moment the write happens.
*   **Scalability:** This approach allows the backend to scale horizontally across multiple instances without needing distributed locks (like Redis Redlock), as the consistency is guaranteed by the database's ACID properties (or atomic write guarantees).
