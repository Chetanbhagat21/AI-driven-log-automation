### Issue Title:
`CRITICAL: Race condition in /api/v1/wallet/withdraw leads to negative account balances`

### Issue Description:
Users are reporting that they can bypass balance checks by sending multiple withdrawal requests simultaneously. Our current logic checks the balance in one query and updates it in another. Under high concurrency, both requests see the original balance, pass the validation, and perform the deduction, resulting in a negative balance.

---

### 1. Root Cause
The vulnerability stems from a **"Read-Modify-Write" anti-pattern** in a concurrent environment. 

The current implementation performs an asynchronous `SELECT` to check the user's balance, followed by an `UPDATE`. Because these operations are not atomic and do not use database-level locking, two concurrent Node.js event loop ticks (or multiple server instances) can read the same balance before the first transaction has committed its update. This is a classic **Lost Update** anomaly.

---

### 2. Fixed Code

#### Before (Vulnerable Code):
```javascript
async function withdraw(userId, amount) {
  const user = await db.query('SELECT balance FROM wallets WHERE user_id = $1', [userId]);
  
  if (user.balance < amount) {
    throw new Error('Insufficient funds');
  }

  const newBalance = user.balance - amount;
  await db.query('UPDATE wallets SET balance = $1 WHERE user_id = $2', [newBalance, userId]);
  return { success: true };
}
```

#### After (Fixed with Row-Level Locking):
```javascript
/**
 * Processes a withdrawal using a pessimistic locking strategy.
 * Uses 'SELECT ... FOR UPDATE' to lock the row until the transaction completes.
 */
async function withdraw(userId, amount) {
  const client = await db.pool.connect();

  try {
    await client.query('BEGIN');

    // 1. SELECT FOR UPDATE locks the row, forcing concurrent requests to wait
    const result = await client.query(
      'SELECT balance FROM wallets WHERE user_id = $1 FOR UPDATE',
      [userId]
    );

    if (result.rows.length === 0) {
      throw new Error('Wallet not found');
    }

    const currentBalance = parseFloat(result.rows[0].balance);

    // 2. Validate balance with locked data
    if (currentBalance < amount) {
      throw new Error('Insufficient funds');
    }

    // 3. Perform the update
    await client.query(
      'UPDATE wallets SET balance = balance - $1, updated_at = NOW() WHERE user_id = $2',
      [amount, userId]
    );

    await client.query('COMMIT');
    return { success: true };
  } catch (error) {
    await client.query('ROLLBACK');
    throw error;
  } finally {
    client.release();
  }
}
```

---

### 3. Explanation

1.  **Database Transactions**: Wrapped the logic in `BEGIN` and `COMMIT` to ensure atomicity. If any step fails, the `ROLLBACK` ensures no partial data is saved.
2.  **Pessimistic Locking (`FOR UPDATE`)**: By adding `FOR UPDATE` to our `SELECT` query, PostgreSQL places a row-level lock on that specific wallet record. If a second request tries to read the same wallet, it will pause and wait until the first transaction commits or rolls back.
3.  **Atomic Update**: Changed the update logic from setting an absolute value (`SET balance = $1`) to a relative calculation (`SET balance = balance - $1`). This further ensures data integrity.
4.  **Resource Management**: Added a `finally` block to call `client.release()`, preventing connection pool exhaustion—a common cause of production outages in Node.js apps.
