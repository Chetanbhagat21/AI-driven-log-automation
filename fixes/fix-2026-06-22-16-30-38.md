### Issue Title:
`[BUG] Concurrent wallet withdrawals allow balance to drop below zero (Race Condition)`

### Issue Description:
Users are reporting that they can withdraw more funds than their current balance by triggering multiple withdrawal requests simultaneously (e.g., clicking the "Withdraw" button rapidly or using a script). 

**Logs indicate:**
1. Request A reads balance: $100.
2. Request B reads balance: $100.
3. Request A validates $100 >= $100, updates balance to $0.
4. Request B validates $100 >= $100, updates balance to -$100.

This violates our business logic where `balance` must never be negative.

---

### 1. Root Cause
The issue is a classic **"Lost Update" race condition**. 

Although Node.js is single-threaded, the database operations are asynchronous. The current implementation follows a "Read-Modify-Write" pattern in the application layer without proper concurrency control. Since the balance check happens in the application code *before* the update is committed, two concurrent requests can both pass the validation check before either has updated the row. 

Node's event loop allows the second request to enter the `withdraw` function while the first request is awaiting the database response.

---

### 2. Fixed Code

We will implement **Pessimistic Locking** using `SELECT ... FOR UPDATE` within a transaction. This ensures that the first request locks the user's row until the transaction is complete, forcing the second request to wait.

```javascript
/**
 * Processes a wallet withdrawal with concurrency protection.
 * @param {string} userId 
 * @param {number} amount 
 */
async function withdraw(userId, amount) {
  const client = await pool.connect();

  try {
    await client.query('BEGIN');

    // 1. SELECT FOR UPDATE: Locks the row until the transaction ends
    const query = {
      text: 'SELECT balance FROM wallets WHERE user_id = $1 FOR UPDATE',
      values: [userId],
    };
    
    const res = await client.query(query);
    
    if (res.rows.length === 0) {
      throw new Error('Wallet not found');
    }

    const currentBalance = parseFloat(res.rows[0].balance);

    // 2. Perform validation
    if (currentBalance < amount) {
      throw new Error('Insufficient funds');
    }

    // 3. Update balance
    const updateQuery = {
      text: 'UPDATE wallets SET balance = balance - $1 WHERE user_id = $2 RETURNING balance',
      values: [amount, userId],
    };

    const updateRes = await client.query(updateQuery);

    await client.query('COMMIT');
    return updateRes.rows[0].balance;

  } catch (error) {
    await client.query('ROLLBACK');
    console.error(`Withdrawal failed for User ${userId}:`, error.message);
    throw error;
  } finally {
    client.release();
  }
}
```

---

### 3. Explanation

1.  **Atomic Transaction:** Wrapped the logic in `BEGIN` and `COMMIT` to ensure that if any part fails, the database state is rolled back.
2.  **Pessimistic Locking (`FOR UPDATE`):** This is the key fix. When Request A executes the `SELECT FOR UPDATE`, the database places a row-level lock on that specific user ID. If Request B tries to read the same row with `FOR UPDATE`, it will be blocked by the DB engine until Request A's transaction is committed or rolled back.
3.  **Application Side Validation:** Even with the lock, we still perform the balance check within the transaction to ensure that by the time a blocked request gets access, it sees the *newly updated* balance.
4.  **Resource Management:** Added a `finally` block to ensure the database client is released back to the pool regardless of whether the operation succeeded or failed, preventing connection leaks.
