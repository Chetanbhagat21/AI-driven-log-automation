### **Example Scenario**
**Issue Title:** Intermittent incorrect wallet balance during concurrent deposit requests.  
**Issue Description:** When a user triggers multiple API calls for a deposit simultaneously, the final balance is often incorrect. It appears some transactions are being ignored or overwritten.

---

### 1. Root Cause
The service was implementing a **Read-Modify-Write** pattern in an asynchronous environment without proper concurrency control.

**The flow was:**
1. Fetch the current balance from the database (`SELECT`).
2. Calculate the new balance in the Node.js application logic.
3. Save the new balance back to the database (`UPDATE`).

When two requests arrived at the same time, both fetched the same initial balance (e.g., $100). Both added $50 locally. Both sent an update command to set the balance to $150. The final result was $150 instead of $200. This is a classic **Race Condition**.

### 2. Fixed Code

#### **Vulnerable Code (Before)**
```javascript
async function deposit(userId, amount) {
    const user = await db.User.findById(userId); // Read
    const newBalance = user.balance + amount;    // Modify
    return await db.User.update(                 // Write
        { id: userId }, 
        { balance: newBalance }
    );
}
```

#### **Fixed Code (Option A: Atomic Update - Recommended)**
```javascript
async function deposit(userId, amount) {
    if (amount <= 0) throw new Error("Invalid amount");

    // Use database-level incrementing to ensure atomicity
    return await db.User.updateOne(
        { _id: userId },
        { $inc: { balance: amount } } // MongoDB example
        // SQL equivalent: SET balance = balance + :amount
    );
}
```

#### **Fixed Code (Option B: Transaction with Pessimistic Locking)**
```javascript
async function deposit(userId, amount) {
    const session = await db.startSession();
    try {
        await session.withTransaction(async () => {
            const user = await db.User.findById(userId).session(session);
            user.balance += amount;
            await user.save({ session });
        });
    } finally {
        await session.endSession();
    }
}
```

---

### 3. Explanation
*   **Atomic Operations:** By using `$inc` (MongoDB) or `SET balance = balance + x` (SQL), we shift the calculation logic from the application layer to the database engine. Databases are designed to handle concurrent writes to the same row/document via internal locking mechanisms, ensuring that every increment is accounted for.
*   **Validation:** Added a basic check for the deposit amount to prevent logical errors.
*   **Performance:** Option A is preferred because it requires a single round-trip to the database and avoids the overhead of managing a full transaction block and row-level locks.
