### Issue Title:
`[BUG] Race condition in /api/v1/withdraw allows users to bypass balance checks`

### Issue Description:
"Under high concurrency (multiple simultaneous requests), users are able to withdraw more funds than their current balance. It appears the balance check passes for multiple requests before the first update is committed to the database. This is causing a significant financial discrepancy in the `accounts` table."

---

### 1. Root Cause
The current implementation follows a **"Read-Modify-Write"** pattern without proper concurrency control. 

1. Request A reads the balance ($100).
2. Request B reads the balance ($100).
3. Request A validates that $100 >= $60 (Withdrawal amount) and proceeds.
4. Request B validates that $100 >= $60 (Withdrawal amount) and proceeds.
5. Request A updates balance to $40.
6. Request B updates balance to -$20.

The application lacks **Atomic Operations** or **Pessimistic/Optimistic Locking** at the database layer to handle concurrent mutations on the same resource.

---

### 2. Fixed Code (Using TypeORM/PostgreSQL)

```javascript
// services/account.service.js

/**
 * FIXED: Uses a database transaction with a Row-Level Lock (SELECT FOR UPDATE)
 * to prevent concurrent race conditions.
 */
async function withdrawFunds(userId, amount) {
    return await dataSource.transaction(async (transactionalEntityManager) => {
        // 1. Fetch the account with a PESSIMISTIC_WRITE lock.
        // This blocks other transactions from reading/writing this row until this tx completes.
        const account = await transactionalEntityManager.findOne(Account, {
            where: { userId: userId },
            lock: { mode: "pessimistic_write" } 
        });

        if (!account) {
            throw new Error("Account not found");
        }

        // 2. Perform the business logic check
        if (account.balance < amount) {
            throw new Error("Insufficient funds");
        }

        // 3. Update the balance
        const newBalance = account.balance - amount;
        await transactionalEntityManager.update(Account, account.id, { 
            balance: newBalance 
        });

        return { success: true, newBalance };
    });
}
```

---

### 3. Explanation
The fix involves two primary architectural changes:

1.  **Database Transactions:** We wrapped the entire operation in a transaction. If any step fails (or the server crashes), the database rolls back to the previous state, ensuring **Atomicity**.
2.  **Pessimistic Locking (`SELECT FOR UPDATE`):** By using `lock: { mode: "pessimistic_write" }`, we tell the database to lock that specific row at the start of the transaction. Any other request trying to read that same account for a withdrawal will be forced to wait until the first transaction commits or rolls back.
3.  **Strict Validation:** The validation happens *after* the lock is acquired, ensuring we are making decisions based on the most current, serialized data.
